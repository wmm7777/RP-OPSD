## 3. 关键发现

1. **MOS 最高的 epoch**: `epoch2.5`（MOS 4.013），最低: `epoch4.0`（MOS 3.989），极差仅 0.024 分。
2. **Badcase 率最低的 epoch**: `epoch1.5`（8.29%），最高: `epoch4.0`（11.01%）。
3. **收敛极早**: epoch 1.0 已达 MOS 3.998，后续 epoch 提升极小，epoch ≥ 3.5 后开始轻度过拟合（badcase 率从 ~8% 升至 ~11%）。
4. **维度对比**: 格式 ≈ 完整性 > 简洁性 > 准确性，语种遵循度全程接近 1。准确性是最弱维度（~4.4），也是主要 badcase 来源。
5. **语种差异**: fr 普遍最高（简洁性 4.85-4.93），zh 在 epoch 4.0 后下降最明显（准确性从 4.45→4.32），过拟合对 zh 影响最大。
6. **过拟合信号**: epoch 4.0/4.5/5.0 的 badcase 率稳定在 ~11%，比 epoch 1.0-2.5 的 ~8-9% 高约 2pp；语种遵循度从 1.0 缓慢降到 0.994（轻微语种漂移）。

## 4. 推荐基线 checkpoint

基于综合表现（MOS 高 + badcase 低），推荐 **sft_ori epoch2.5**（MOS 4.013，badcase 9.06%）作为后续对照实验基线：
- 它是 1.5 之后的次高点，MOS 与 epoch1.5 几乎并列（4.013 vs 4.012），但 badcase 略高（9.06% vs 8.29%）
- 如果更看重稳定性（badcase 最低），选 epoch1.5（badcase 8.29%）
- 如果要等量比较「多训有无收益」，epoch1.0 和 epoch5.0 都可作为端点对照

## 7. 各语种最优 epoch 不同的原因

| 语种 | MOS 最优 | badcase 最优 | 收敛特征 |
|---|---|---|---|
| en | epoch3.0 (4.002) | epoch1.0 (8.76%) | 最平坦，全程 3.98–4.00 震荡 |
| fr | epoch2.0 (4.060) | epoch3.0 (5.45%) | 最稳定、badcase 最低、最优窗最长 |
| ru | epoch1.5 (4.021) | epoch1.5 (6.85%) | 早到顶，epoch≥2.0 后持续下滑 |
| zh | epoch1.5 (4.020) | epoch1.0 (7.34%) | 1.5 后崩得最快，epoch4.0 跌至 3.962 |

各语种峰值错开（ru/zh=1.5，fr=2.0，en=3.0），三层原因：

1. **测试集本身不同（首要混淆因素）**：四语种各 220 张测试图基本完全不相交（两两交集 ≤1），"语种"轴与"测试内容难度"轴强耦合。所谓"zh 最优在 1.5"同时反映 zh 这批图本身更难。
2. **预训练稀有度决定过拟合速度**：fr（拉丁字母，分布充足）上升期长、下降期缓；ru（西里尔字母）与 zh（CJK）在 9B 模型里覆盖弱，先到顶先过拟合，zh 因含大量非中文源图（阿姆哈拉/他加禄）跨脚本转写最易崩。
3. **错误性质不同，多训放大而非修复**：en 卡在跨脚本 OCR、zh 卡在幻觉（如把阿姆哈拉预算新闻编成"广播频率 125.4 MHz"），ru 卡在主客体颠倒+语种漂移——这些瓶颈靠加 epoch 都解不掉，反而让模型"越训越敢编"。

### 8.2 本质问题（三层）

1. **ai-gold 能读对**（9 张中 7 满分，2 张俄文仅 14a→14 小错）——教师级模型能感知这些脚本。
2. **9B 与 30B-A3B 同样读不对，错法一致**——Qwen3.5 族视觉塔在阿姆哈拉/阿拉伯/乌尔都/部分西里尔上有**系统性盲点**，放大模型不解决。
3. **蒸馏（§5 sft_gold_397b）救不了**——9 张里没有 1 个被真正读对，蒸馏后只产生两种结局：
   - **退化为"安全但丢信息"**：阿姆哈拉任命/预算 → 只说"男子演讲/会议现场"，干脆不读脚本（用回避换不犯错）；
   - **编出另一个错读**：账号名 አዲስ መጽሐፍ → አይዮን ሚዛ；城市 阿齐济耶 → 的黎波里/班加西；俄文协议 → 编成"交通违章"。

**根因**：SFT 只教输出分布，不教感知。学生看到同样的阿姆哈拉字形依然解码不出——蒸馏只让它学会"读不准时换个说法"，**没有把 OCR 能力装进视觉塔**。教师能读 ≠ 学生能读，因为感知发生在视觉塔，而 SFT 的"输出对齐"梯度不足以重塑视觉表征。

### 8.3 与 §7 的关系

§7 描述的"各语种最优 epoch 不同"主要源于测试集不相交（混淆因素）+ 稀有脚本过拟合更快，**但 epoch 选择本身不是解法**——无论选哪个 epoch，这 9 张跨脚本顽固 badcase 都解不掉，且 §3.3 的"收敛极早、epoch≥3.5 过拟合"在统计上成立（9 个 checkpoint MOS 全在 1 个标准误 SE≈0.009 内，epoch1→5 为 -0.008 负收益）。

## 9. 修正后的解法排序

| 方案 | 对跨脚本瓶颈有效 | 判断 |
|---|---|---|
| §5 gold_397b SFT | ✗ | §8 已证无效，治不了感知。可作基线对照确认这一点，别指望破天花板 |
| 30B 同族放大 | ✗ | 9B=30B 同盲点 |
| **前置 OCR**（PaddleOCR/Tesseract/Cloud，支持 amh/ben/urd/ara/rus） | ✓ | **唯一确定有效**，绕过 Qwen 视觉塔盲区，把脚本文字抽出注入 prompt |
| 跨脚本数据增强 + 视觉塔继续预训练 | ✓ | 唯一改模型自身的路，端侧 MNN 必选，周期长 |
| RP-OPSD/VOPD reward-free 自蒸馏 | ✗ | 学生自己读不对，reward-free 无纠正信号，只会强化盲点 |

**建议**：前置 OCR 先上（立竿见影，生产侧可用）；视觉塔跨脚本继续预训练并行启动（端侧治本）；§5 gold SFT 与 RP-OPSD 降优先级，作为"确认它们治不了感知"的对照实验而非破局点。

> 验证假设：9 张顽固图读不对，是因为"字小 < 1 视觉 token"还是"视觉塔根本不认识这些字形"？Qwen3.5-9B 视觉塔 patch_size=16 + spatial_merge_size=2 → 32px/token；源图宽 ~500px，字形 ~10-14px。放大让字形跨更多 token 看是否救回。脚本 `infer/resolution_ab_test.py`，结果 `bad9_resolution_ab.json`，人工逐条判定（关键词判据过松已弃用）。

**关键分裂**：
- **拉丁字母 + 西里尔字母**（mHx / P5X / HBb / 2Ov）：放大 2x/4x 有效——模型本就会这些字母，只是字小被 token 化碾掉，放大到够 token 就能读对人名/书名/疾病/地点。**mHx 4x 从漏名直接变全对**。
- **阿姆哈拉 / 孟加拉 / 乌尔都**（3TA / Njt / hbe / 8JF）：放大无效——放大只增加像素不增加字形知识，模型对这些字形没有足够预训练表征，放大再多也认不出，只会换一种方式编（Njt native 编"频道"、4x 编"选举日期"；3TA 4x 编另一个错名）。
- **阿拉伯**（BMX）：不稳定，2x 部分对、4x 又错。

**对 §9 解法的修正**：
1. **放大分辨率不是银弹，但对"会-但-字小"的脚本（拉丁/西里尔）零成本有效**——生产侧加一步 LANCZOS 2x 预处理就能救 mHx/P5X/HBb/2Ov 这类 badcase，端侧 MNN 也能做（CPU 放大）。这部分占跨脚本 badcase 的约一半。
2. **对阿姆哈拉/阿拉伯/孟加拉/乌尔都，放大救不了**——这些字形在视觉塔里根本没有表征，必须走 ①专用 OCR（PaddleOCR 能认这些字形）或 ②视觉塔在这些脚本上继续预训练补字形表征。
3. **盲点本质被精确化**：不在"分辨率不够"（放大证明分辨率对会-但-字小的脚本有效），而在"视觉塔对阿姆哈拉等罕见脚本字形缺乏预训练表征"——这正是 §8 蒸馏救不了的根因（教师能读因为教师 LLM 强/预训练足，但学生视觉塔没装这些字形表征，SFT 输出对齐传不过去）。
